# 故障排查 / Troubleshooting

zh — 按症状定位。日志位置：`logs/stdout.log` 与 `logs/stderr.log`（`start.sh` 启动时）。en — locate by symptom. Logs live in `logs/stdout.log` and `logs/stderr.log` (when started via `start.sh`).

## 服务起不来 / Service fails to start

zh — 症状：`start.sh start` 报 "port ... not registered ... refusing to start"。
en — Symptom: `start.sh start` prints "port ... not registered ... refusing to start".

zh — 原因：端口自检失败（#36 引入，fail-fast 代替 CI 后置发现）。修复：在 `~/fusion/architecture/port-registry.yaml` 确认 `fusion-bench: port: 11467` 存在；临时绕过用 `FUSION_SKIP_REGISTRY_CHECK=1`（输出 warn）；独立部署无注册表时仅 warn 不阻断。改端口必须同时改注册表 + 项目配置并跑 `python scripts/check-ports.py`。
en — Cause: the registry self-check (#36) fails fast instead of waiting for CI. Fix: confirm `fusion-bench: port: 11467` exists in `~/fusion/architecture/port-registry.yaml`; bypass temporarily with `FUSION_SKIP_REGISTRY_CHECK=1` (warns); a missing registry file only warns for standalone deploys. Any port change requires registry + project config edits plus `python scripts/check-ports.py`.

zh — 症状：`No module named fusion_bench.api.server`（历史版本）。
en — Symptom: `No module named fusion_bench.api.server` (historical).

zh — 该模块已移除；`start.sh` 现调用 `python3 -m fusion_bench.cli serve`。若手动构造启动命令，一律走 CLI `serve`（FastAPI 应用在 `fusion_bench/api/app.py`）。
en — that module was removed; `start.sh` invokes `python3 -m fusion_bench.cli serve`. Build any custom launch on the CLI `serve` command (FastAPI app in `fusion_bench/api/app.py`).

## 请求 401 / Requests return 401

zh — 服务 fail-closed：缺 `X-Tenant-Id`、缺/错 `Authorization: Bearer`、token 非 fusion-identity 签发、`jwt.tid` 与头不一致、租户停用，全部 401，无默认租户降级。排查顺序：
en — the service is fail-closed: missing `X-Tenant-Id`, missing or wrong bearer, a token not issued by fusion-identity, a `jwt.tid`/header mismatch, or an inactive tenant all return 401 with no fallback. Check in order:

1. zh — fusion-identity（默认 `:11470`）是否在运行，`FUSION_IDENTITY_URL` 是否指向它。en — is fusion-identity (default `:11470`) up, and does `FUSION_IDENTITY_URL` point at it.
2. zh — token 是否新鲜、租户是否 active。en — is the token fresh and the tenant active.
3. zh — CLI 侧上游 401：设置 `FUSION_CLIENT_KEY`（或旧名 `FUSION_MLX_API_KEY`）；prod 缺失会抛 `RuntimeError`，dev 为空串 + 一次性 warn。en — for upstream 401s from the CLI side, set `FUSION_CLIENT_KEY` (alias `FUSION_MLX_API_KEY`); missing in prod raises `RuntimeError`, in dev it is an empty string plus one warn.

zh — shell 嵌入模式 401：网关代理注入的是模块密钥 `FUSION_BENCH_SHELL_API_KEY`；确认 `start.sh` 生成的 `.fusion-bench-shell-key` 与网关注入值一致（注册体与校验器必须同一值），且网关注册 upstream 指向 `http://127.0.0.1:11467` 而不是 vite 开发端口 11474（后者是 dev-only，历史上导致 `backend_unavailable`）。
en — for embedded shell 401s: the gateway proxy injects the module key `FUSION_BENCH_SHELL_API_KEY`; confirm the `.fusion-bench-shell-key` generated by `start.sh` matches the value the gateway injects (registration body and validator must agree), and that the gateway upstream is `http://127.0.0.1:11467`, not the dev-only vite port 11474 (which historically produced `backend_unavailable`).

## 嵌入界面打不开 / Embedded UI does not load

zh — 症状：`/shell/fusion-bench/` 打开 404 或白屏。检查：`web/dist/index.html` 是否存在（不存在时 `start.sh` 会尝试 `bun run build`，bun 缺失或构建失败仅 warn，API 照常服务但 UI 不可用）；`FUSION_BENCH_DISABLE_UI` 是否误设；重新 `./start.sh restart` 让注册携带正确 upstream。
en — Symptom: `/shell/fusion-bench/` returns 404 or a blank page. Check that `web/dist/index.html` exists (when missing, `start.sh` attempts `bun run build`; failure only warns and the API serves without UI), that `FUSION_BENCH_DISABLE_UI` is not set, and restart via `./start.sh restart` so registration carries the correct upstream.

zh — 嵌入模式下接口 401 但页面正常：历史上 SPA 用根相对 `/api/...` 导致请求逃出 `/shell/fusion-bench/` 子路径打到网关自身；已修复为 `apiBase()` 从 `window.location.pathname` 推导。若自行改前端，保持相对基址。
en — if pages load but API calls 401 in embedded mode: the SPA once used root-relative `/api/...` URLs that escaped the `/shell/fusion-bench/` sub-path; it now derives the base from `window.location.pathname`. Keep the relative base in any frontend change.

## 数字可疑 / Numbers look wrong

zh — 速度类指标必须注明路径：默认网关 `:11432`，直连用 `--direct-mlx`；结果 meta 与报告记录 `gateway` / `direct-mlx`，对比数字前先确认同路径。profiler 的引擎侧与 agent 侧延迟键永不合并，跨 backend 不能直接平均（`backend` 键必填）。full-trace 模式有真实每 token 开销，不要在 CI 开启。TTFT/prefill 口径见 [architecture.md](architecture.md) 的"度量完整性"。
en — speed numbers must cite their path: gateway `:11432` by default, direct via `--direct-mlx`; result meta and reports record `gateway` / `direct-mlx`, so confirm both sides used the same path before comparing. Profiler engine-side and agent-side latency keys are never merged and cross-backend numbers must not be averaged (the `backend` key is mandatory). Full-trace mode adds real per-token overhead — keep it off in CI. See the metric-integrity section in [architecture.md](architecture.md).

zh — 结果疑似旧缓存：`fusion-bench cache stats` 查看，`fusion-bench cache clear --model M --task T` 清理后重跑。
en — results may be cached: inspect with `fusion-bench cache stats` and clear with `fusion-bench cache clear --model M --task T` before rerunning.

## 进程管理 / Process management

zh — `ps -axww -o comm` 应显示 `fusion-bench serve :<port>` 形式的进程标题（setproctitle，缺库时安全降级）。裸 `Python` 进程标题视为缺陷。PID 在 `.fusion-bench.pid`；`./start.sh stop` 最多等 5 秒后强杀。重启后 shell 菜单入口消失通常是网关心跳（30 秒过期）未续上——`start.sh` 已默认 `FUSION_SHELL_GATEWAY_URL=http://127.0.0.1:11432` 开机自注册。
en — `ps -axww -o comm` should show a `fusion-bench serve :<port>` process title (setproctitle, safe fallback when missing); a bare `Python` title is a defect. The PID lives in `.fusion-bench.pid`; `./start.sh stop` force-kills after 5 seconds. A missing shell menu entry after a reboot means the gateway heartbeat (30s expiry) lapsed — `start.sh` now defaults `FUSION_SHELL_GATEWAY_URL=http://127.0.0.1:11432` so registration survives restarts.

zh — Docker 容器启动即崩并报 `unable to open database file`：通常是命名卷根归属 root；镜像已预建 `~/.fusion-bench` 与 `~/bench` 并 chown 给非 root `fusion` 用户，自建卷时保持同样归属。
en — a Docker container crashing at startup with `unable to open database file` usually means a root-owned named volume; the image pre-creates `~/.fusion-bench` and `~/bench` owned by the non-root `fusion` user — keep that ownership for custom volumes.

zh — 以上排查无效时，运行 `pytest tests/` 确认套件本身健康（本仓库 727 项测试为绿灯基线），再提 issue 附 `logs/stderr.log` 摘要。
en — if nothing above helps, run `pytest tests/` to confirm the suite itself is healthy (the 727-test suite is the green baseline), then file an issue with a `logs/stderr.log` excerpt.
